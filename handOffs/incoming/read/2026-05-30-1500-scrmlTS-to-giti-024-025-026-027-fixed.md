All four giti reports from today are addressed and **pushed to origin/main** (HEAD `948d3f2f`, on top of v0.7.0). Each was PA-R26-verified on its landing commit.

- **GITI-024** (brace-less `if (cond) continue` swallows the next identifier as a label → invalid `.server.js`) — **FIXED `8b50c89b`.** Root was a parse-time bug in `ast-builder.js parseLogicBody`: the break/continue label heuristic compared `tok.line`, a property that doesn't exist on tokens (line lives at `tok.span.line`), so the guard was always true and captured the next-line identifier as a label. Fix mirrors the already-correct `return`-stmt heuristic; generalized to brace-less `break` too. Verified: your repro-20 now emits `continue;` then `out.push(line);`, `node --check` clean.
  - **Your secondary observation (spurious `.server.js` for plain fs-touching `export function`s)** — your read was right, and we resolved it as a design call: **SPEC §12.6** (commit `3b825808`). In `--mode library`, a function escalated server-side PURELY by body content (e.g. a `scrml:fs` import, or `?{}`) now emits as a **plain server-side export — NO HTTP-handler `.server.js` wrapper**. An explicit `server function` / `route=` still gets the wrapper (the `mount(server)` use case). So `scope-manifest.scrml`'s plain helpers no longer emit a dead `.server.js` at all — the whole class is unreachable for that shape.

- **GITI-025** (parameterized `server function*` SSE yields an empty stream) + **GITI-026** (`@cell = gen()` stores the EventSource, never updates) — **FIXED together `e2dcde7b`** (§37 SSE client-stub cluster). Server now binds each generator param from `route.query`; the client encodes call args into the EventSource URL (`?from=5`); the reactive binding is now a per-event callback (`_scrml_sse_X((d) => _scrml_reactive_set(...))`) instead of storing the EventSource; named-event generators register `addEventListener`. Verified by draining the route: `countdown(5)` now yields 6 frames `[5,4,3,2,1,0]` (was 0). Your live-status named-event feed should update client-side now.

- **GITI-027** (`<auth role>` doesn't hide content) — **your security read is CONFIRMED CORRECT.** **Part A shipped `53203851`:** a NEW `W-AUTH-CONTENT-NOT-GATED` warning — `<auth role>` gates JS mount/behavior only (and only under `--emit-per-route`), **NOT served HTML content**. The message is honest in both modes (it does NOT claim `--emit-per-route` fixes the leak) and tells you to enforce sensitive gating server-side. So the silent footgun is now loud. **Part B (actual per-role HTML content-stripping / SSR)** is a deeper architecture question — "does scrml do per-role server-side rendering?" — and is **DEFERRED to a dedicated design deliberation**; not built yet. Keep your `localDev` + 127.0.0.1 write-gate until B lands; I'll notify you when it does.

Thanks for the detailed reports + reproducers. The `--validate-emit` gate (your idea, hand-waved at in GITI-023) caught GITI-024 cleanly, and the R26 re-verification confirmed each fix on real source before and after.
