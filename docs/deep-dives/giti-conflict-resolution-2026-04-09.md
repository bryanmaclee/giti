# Deep Dive: giti Conflict Resolution -- Text Markers vs Structured vs Compiler-Assisted

**Date:** 2026-04-09
**Scope confirmed:** yes
**Feeds into:** giti VCS model decision | debate on merge conflict UX | parent deep dive at `docs/deep-dives/giti-radical-doubt-2026-04-09.md`

---

## Scope

**Question:** How should giti handle merge conflicts -- git's text markers, jj's structured data model, Pijul's mathematical approach, or a novel compiler-assisted model that leverages scrml's AST knowledge?

**In scope:**
- Git's three-way merge algorithm and why text-based conflict markers fail
- jj's conflict-as-data model with deferred resolution and propagation
- Pijul's category-theory patch model and what conflicts it eliminates
- AST-based merge tools (Mergiraf, Weave, SemanticMerge, IntelliMerge) and their results
- Compiler-assisted resolution using scrml's type system and AST visibility
- The "no conflicts" philosophy (trunk-based development + feature flags)
- What percentage of conflicts are auto-resolvable with each approach

**Out of scope:**
- giti's collaboration primitive (PRs vs stacked diffs -- separate sub-deep-dive)
- giti's underlying VCS engine choice (git vs jj vs custom -- separate sub-deep-dive)
- Implementation timeline or effort estimates

## Context

### What we already know

**Parent deep dive (giti-radical-doubt-2026-04-09.md) established:**
- 87% of developers have encountered merge conflicts (hutte.io statistics)
- 65% of developers have lost commits or changes
- Git dumps conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) into source files -- parent deep dive Category B4 calls these "text-editing puzzles"
- Bryan's design constraint #6: "Conflicts as data, not text puzzles. Pijul and jj both demonstrate this."
- The Casey expert's Pattern 3: "The correct number of merge strategies for most teams is one."

**giti v1 debate result (design-insights.md, 2026-04-08):**
Casey/Handmade approach won (50.5 > Fossil 46.5). The winning insight: giti's data model should be expressed in scrml's state types. PRs, reviews, issues as typed state machines.

**scrml compiler capabilities (memory: project_living_compiler.md, project_meta_as_capability_guarantee.md):**
The scrml compiler has full AST visibility during compilation. Every scrml file starts with `<program>` and is parsed into a typed AST. State types (`< Thing>`) define data shapes with transition rules. The compiler already tracks type information, import graphs, and downstream usages.

## Academic Data: How Many Conflicts Are Auto-Resolvable?

This data is critical for evaluating each approach. Sources: multiple academic studies (2020-2024).

- **56% of textual conflicts** are resolved by developers keeping only the local or remote version -- they are trivially resolvable if a tool can predict which side to keep. Source: study of 616 textual conflicts, cited in EASE 2024 paper "Towards Semi-Automated Merge Conflict Resolution."
- **70.5% of conflicts** can be automatically resolved by MESTRE, a tool that predicts merge conflict resolutions based on the most frequent resolution strategies. Source: ScienceDirect, "Automatic prediction of developers' resolutions for software merge conflicts" (2023).
- **86% of textual conflicts** have resolutions that can theoretically be generated by existing tools, but the tools cannot guarantee selecting the correct resolution. Source: same EASE 2024 paper.
- **Weave (entity-level semantic merge)** resolves **31/31 benchmark scenarios cleanly vs Git's 15/31** -- a 100% clean resolution rate on its benchmark set where Git only achieves 48%. On larger repos: 39 wins on Git's own C codebase, 14 wins on Flask, zero regressions in either case. Source: github.com/Ataraxy-Labs/weave.
- **99% of conflicting methods** in one study of 779 Java conflicts were resolved by keeping only one version. Source: cited in EASE 2024 paper, granularity at method level.

**Key insight:** The majority of conflicts that developers encounter are structurally trivial -- one side wins. The hard conflicts (both sides changed the same entity in incompatible ways) are a minority but consume disproportionate time and frustration.

## Approaches

### Approach A: jj-Style Conflicts as Data (Structured Storage, Deferred Resolution)

**How it works:** Conflicts are stored as first-class objects in the commit graph, not as text markers in files. A conflicted state is just another commit. The internal representation stores the conflicting trees (not textual markers), allowing conflicts to be committed, propagated, and resolved later.

jj uses a "snapshot + diff" conflict marker format:
```
<<<<<<< Conflict 1 of 1
%%%%%%% Changes from base to side #1
 apple
-grape
+grapefruit
 orange
+++++++ Contents of side #2
 apple
 grape
 pineapple
 orange
>>>>>>> Conflict 1 of 1
```

The `%%%%%%%` section shows what one side changed (as a diff). The `+++++++` section shows what the other side looks like (as a snapshot). This is strictly more informative than git's markers because you can see both the intent of one change and the full context of the other.

**Critical feature: deferred resolution.** You can commit a conflict and keep working. Descendant commits carry the conflict forward. When you eventually resolve it, jj auto-rebases all descendants. This eliminates the "stop everything and resolve this conflict NOW" interrupt that git imposes.

**Critical feature: no nested markers.** What's stored in the commit is a logical representation, not conflict markers. Rebasing a conflict does not produce nested `<<<<<<<` inside existing `<<<<<<<` -- a notorious git failure mode.

**scrml example (giti PR with jj-style conflict):**
```scrml
<program>
  // Developer A changed Button's props
  < Button>
    label: string
    variant: .Primary | .Secondary
  </ Button>

  // Developer B changed Button's props differently
  // In giti, this is stored as a conflict OBJECT, not markers in the file.
  // The giti UI shows:
  //
  // CONFLICT in Button state type:
  //   Base:   < Button> label: string </ Button>
  //   Side A: < Button> label: string, variant: .Primary | .Secondary </ Button>
  //   Side B: < Button> label: string, size: .Small | .Medium | .Large </ Button>
  //
  // Resolution options:
  //   [1] Keep both (label + variant + size)
  //   [2] Keep A only (label + variant)
  //   [3] Keep B only (label + size)
  //   [4] Manual edit
</program>
```

**Gains:**
- Conflicts are data, not text pollution -- addresses Bryan's constraint #6 directly
- Deferred resolution eliminates the "stop everything" interrupt
- No nested conflict markers (a git failure mode eliminated entirely)
- Conflict propagation to descendants is automatic
- Proven model: jj is actively developed, Google-backed, growing adoption

**Loses:**
- Still fundamentally text/tree-level -- does not understand scrml semantics
- Requires giti to implement jj's conflict storage model (significant engineering)
- Conflict markers, while better than git's, are still markers in files when materialized

**Complexity:**
- VCS engine: High (must implement conflict-as-data storage)
- Platform UI: Medium (must render conflicts as structured data)
- Developer mental model: Low (conflicts are visible, deferrable, reversible)

**Prior art:**
- jj (Jujutsu): This IS jj's model. Growing adoption, pre-1.0 (v0.24 as of Dec 2024). Source: docs.jj-vcs.dev, github.com/jj-vcs/jj
- Darcs: Original inspiration for conflict-as-data. Suffered from exponential merge performance. Pijul fixed the performance issue. Source: jneem.github.io

### Approach B: Pijul-Style Mathematical Patches (Commutative, CRDT-Based)

**How it works:** Files are stored as directed acyclic graphs (DAGs) of lines rather than sequential text. Patches are defined mathematically using category theory (pushouts). Two independent patches are commutative -- they can be applied in any order and produce the same result. Conflicts only arise when patches genuinely depend on each other and change the same thing incompatibly.

Pijul implements a conflict-free replicated datatype (CRDT) that models text files. The merge operation is the pushout in the category of patches -- for every pair of operations there is a unique composition such that the diagram commutes.

**What conflicts remain:** Even with commutative patches, conflicts occur when two patches modify the same lines in incompatible ways. Pijul does not eliminate conflicts -- it eliminates false conflicts (ordering-dependent conflicts) and guarantees that all merges produce the same result regardless of order.

**scrml example (Pijul-style conflict-free scenario that WOULD conflict in git):**
```scrml
<program>
  // Base version
  < TodoList>
    items: [< Todo>]
    filter: .All | .Active | .Completed
  </ TodoList>

  // Developer A adds a sort field (at end of type)
  // Developer B adds a search field (at end of type)
  //
  // In git: CONFLICT (both added lines at the same position)
  // In Pijul-style: NO CONFLICT (patches are independent, commutative)
  //
  // Result (either order):
  < TodoList>
    items: [< Todo>]
    filter: .All | .Active | .Completed
    sort: .ByDate | .ByPriority | .ByName
    search: string
  </ TodoList>
</program>
```

**Gains:**
- Eliminates an entire class of false conflicts (ordering-dependent)
- Mathematically proven correctness -- merges are deterministic regardless of order
- Logarithmic time for non-conflicting patches (vs potential exponential in darcs)

**Loses:**
- Not Git-compatible -- giti would need a custom VCS engine
- Near-zero ecosystem adoption (Pijul's "the Nest" platform has almost no users)
- The theory is sound but the implementation is less battle-tested
- Files-as-DAGs is a fundamentally different storage model -- tooling must be rebuilt
- Proves that technical superiority does not create adoption (parent deep dive conclusion)

**Complexity:**
- VCS engine: Very High (implement category-theory-based patch algebra)
- Platform UI: Medium (conflicts that DO occur still need resolution UI)
- Developer mental model: Medium (the math is invisible, but "patches commute" requires some understanding)

**Prior art:**
- Pijul: This IS Pijul's model. Published theory, working implementation, near-zero adoption. Source: pijul.org, jneem.github.io
- Darcs: Predecessor. Same theory, exponential performance bug. Pijul solved the performance issue. Source: jneem.github.io/merging
- CRDTs (conflict-free replicated data types): Used in collaborative editing (Google Docs, Figma). Proven in that domain. Source: general CRDT literature

### Approach C: AST-Aware Semantic Merge (Mergiraf/Weave Model)

**How it works:** Instead of merging text lines, parse all three versions (base, left, right) into abstract syntax trees using a parser (tree-sitter or scrml's own parser). Match entities across versions by identity (name + type + scope). Only conflict when two branches change the same semantic entity incompatibly. Independent changes to different entities in the same file merge cleanly.

Two existing tools demonstrate this:

**Mergiraf:** Syntax-aware merge driver for git. Uses tree-sitter to parse into ASTs. Falls back to line-based merge when AST merge is unnecessary (optimization). Supports 33 languages. Uses GumTree algorithm for tree matching. Source: mergiraf.org, codeberg.org/mergiraf/mergiraf.

**Weave:** Entity-level semantic merge. Operates on semantic entities (functions, classes, methods, imports) extracted via tree-sitter. Benchmark: 31/31 clean merges vs git's 15/31. Zero regressions on large repos. Source: github.com/Ataraxy-Labs/weave.

**scrml example (semantic merge that git would conflict on):**
```scrml
<program>
  // Base version has two components:
  < Header>
    title: string
    subtitle: string
  </ Header>

  < Footer>
    links: [string]
    copyright: string
  </ Footer>

  // Developer A modifies Header (adds nav prop)
  // Developer B modifies Footer (adds social prop)
  //
  // Git: CONFLICT if both edits are near each other in the file
  // AST merge: NO CONFLICT -- Header and Footer are different entities
  //
  // Developer A modifies Header AND Developer B modifies Header:
  // AST merge: CONFLICT only if they changed the SAME field
  //            NO CONFLICT if A added nav and B added theme (different fields)
</program>
```

**What conflicts remain hard even with AST knowledge (from academic research):**

1. **Semantic conflicts:** One branch renames a function, another branch adds a call to the old name. The merge succeeds syntactically but the program is broken. Source: Martin Fowler, "bliki: Semantic Conflict"; Sousa et al., "Verifying Semantic Conflict-Freedom in Three-Way Program Merges" (2018).

2. **Cross-entity dependencies:** Branch A changes a function's return type, Branch B adds code that depends on the old return type. AST merge cannot detect this without type checking. Source: ACM DL, "Detecting Build Conflicts in Software Merge for Java Programs" (2022).

3. **Method signature changes:** Renames, parameter reordering, parameter type changes. Tools like SafeMerge "currently do not support renamed methods or methods with parameter reordering, introduction, or deletion." Source: same 2022 ACM paper.

**The academic consensus:** "Automatic resolution of semantic conflicts is not possible, and while tools may eventually tackle some of them, some gnarly ones will likely always require human intervention." Source: arxiv.org, semistructured merge paper (2024).

**Gains:**
- Eliminates false conflicts caused by independent changes in the same file
- Weave's 31/31 vs git's 15/31 benchmark is a 2x improvement in clean merges
- Works as a layer on top of any VCS (git, jj, custom) -- not mutually exclusive with other approaches
- Tree-sitter support for scrml could be built (or scrml's own parser used directly)

**Loses:**
- Cannot resolve semantic conflicts (cross-entity dependencies, type mismatches)
- Requires a parser for every supported language (scrml-only initially is fine, but giti may host polyglot repos)
- AST merge is more expensive than text merge (Mergiraf optimizes by trying text first)
- Still requires manual resolution for genuinely hard conflicts

**Complexity:**
- VCS engine: Low (works as a merge driver on top of any VCS)
- Platform UI: Medium (can show entity-level diffs instead of line diffs)
- Compiler integration: Medium (scrml parser already exists; exposing it for merge is new work)

**Prior art:**
- Mergiraf: Production-ready, 33 languages, Rust + tree-sitter. Active development. Source: mergiraf.org
- Weave: Entity-level, 26 languages, impressive benchmarks. Source: github.com/Ataraxy-Labs/weave
- SemanticMerge (Plastic SCM): The original AST merge tool (2013). Used Roslyn for C#. Acquired by Unity, standalone version discontinued (end of availability announced on Plastic SCM forums). Source: plasticscm.com, forum.plasticscm.com
- IntelliMerge: Academic (ACM 2019). Graph-based, refactoring-aware, Java-only. Source: dl.acm.org/doi/10.1145/3360596
- Spork (KTH): AST-based structured merge for Java. Recommends Mergiraf for production use. Source: github.com/ASSERT-KTH/spork
- Mastery: Shifted-code-aware structured merging. Tested on 40,533 merge scenarios from 78 Java projects. Source: paulz.me

### Approach D: Compiler-Assisted Resolution (scrml-Native, Novel)

**How it works:** Since scrml has a compiler with full type information, giti can go beyond AST-level merging to type-level merging. The compiler can:

1. Parse both sides into typed ASTs (not just syntax trees -- typed trees with resolved imports, state type definitions, and transition rules)
2. Detect breaking changes at the type level ("Button gained a required prop -- 3 downstream files will break")
3. Auto-resolve conflicts that are type-safe (two branches adding different non-conflicting fields to the same state type)
4. Flag conflicts that would compile but produce wrong behavior (semantic conflicts detected via type checking the merged result)

This extends Approach C by adding the type checker as a merge validator.

**scrml example (compiler-assisted merge):**
```scrml
<program>
  // Base version
  < UserCard>
    name: string
    email: string
  </ UserCard>

  // Developer A adds avatar field and uses it in template
  // Developer B adds role field and adds a role-based conditional

  // The compiler merges the state type:
  < UserCard>
    name: string
    email: string
    avatar: string    // from A
    role: .Admin | .User | .Guest  // from B
  </ UserCard>

  // The compiler then TYPE-CHECKS the merged result:
  //   - A's template references avatar: OK (avatar exists in merged type)
  //   - B's conditional references role: OK (role exists in merged type)
  //   - No field was modified by both sides
  //   - RESULT: Auto-merged, zero conflicts
  //
  // But if Developer A had changed email from string to Email (a refinement type)
  // and Developer B had added code that passes email to a function expecting string:
  //   - CONFLICT: type mismatch in merged result
  //   - The compiler shows: "email changed from string to Email by A,
  //     but B's sendNotification(user.email) expects string"
</program>
```

**What this catches that AST-only cannot:**

| Scenario | AST merge (Approach C) | Compiler-assisted (Approach D) |
|----------|----------------------|-------------------------------|
| Two branches add different fields to same state type | Clean merge | Clean merge + type-checked |
| Branch A changes field type, Branch B uses old type | Clean merge (BROKEN CODE) | CONFLICT flagged |
| Branch A removes a state variant, Branch B matches on it | Clean merge (BROKEN CODE) | CONFLICT flagged |
| Branch A adds required prop, Branch B adds new usage without it | Clean merge (BROKEN CODE) | CONFLICT flagged |

**Gains:**
- Catches semantic conflicts that no other approach can detect
- Auto-resolves more conflicts safely (because type checking validates the merge)
- Produces the best possible conflict messages ("email changed from string to Email by A, but B's sendNotification expects string" vs `<<<<<<< HEAD`)
- Unique to scrml -- no other VCS has a compiler-integrated merge
- Aligns with scrml's philosophy: "compiler is dev's best friend" (memory: feedback_compiler_best_friend.md)

**Loses:**
- Requires the scrml compiler to expose merge-specific APIs
- Only works for .scrml files -- polyglot repos need fallback to Approach C or text merge
- Compiler must be invokable during merge (performance concern for large repos)
- No prior art -- entirely novel, high implementation risk
- If the compiler has bugs, merges could silently produce wrong results

**Complexity:**
- VCS engine: Low (works as a merge driver, like Approach C)
- Compiler integration: High (compiler must expose type-diff and merge-validation APIs)
- Platform UI: Medium-High (must render type-level conflict information)
- Spec complexity: Medium (needs specification of merge behavior for each language construct)

**Prior art:**
- **No direct prior art exists.** Search for "version control built into programming language," "compiler-integrated VCS," "type-aware merge tool," and "compiler merge resolution" returned zero results for a VCS that uses a language's own compiler for merge resolution. Source: WebSearch, multiple queries.
- **Partial prior art -- SemanticMerge + Roslyn:** SemanticMerge used Roslyn (C# compiler infrastructure) for parsing and semantic analysis during merge. It could detect code moves and refactorings. But it did not use the type checker to validate merge results. Discontinued as standalone product. Source: semanticmerge.com, forum.plasticscm.com.
- **Partial prior art -- IDE merge tools:** IntelliJ IDEA's merge wizard auto-resolves "trivial" conflicts using language-specific knowledge. But this is a UI tool, not a VCS primitive. Source: jetbrains.com.

### Approach E: Workflow-Level Conflict Prevention (Trunk-Based + Feature Flags)

**How it works:** Instead of resolving conflicts better, prevent them from occurring. Trunk-based development means everyone commits to a single branch. Feature flags wrap incomplete features so they can be committed without being active. Long-lived feature branches -- the primary source of complex conflicts -- are eliminated.

**scrml example (feature flag in scrml):**
```scrml
<program>
  ${ import { featureEnabled } from 'giti/flags' }

  < TodoApp>
    items: [< Todo>]
    filter: .All | .Active | .Completed

    // New feature behind a flag -- committed to trunk immediately
    ${
      if (featureEnabled('todo-priorities')) {
        // This code exists in trunk but is inactive
      }
    }
  </ TodoApp>

  // No long-lived branch = no merge conflicts
  // Feature is toggled on when ready, not merged in
</program>
```

**Gains:**
- Eliminates the root cause of most conflicts (long-lived branches diverging)
- Proven at scale: Google, Meta, and other large engineering orgs use trunk-based development
- Simplifies the VCS model (one branch, linear history)
- Compatible with any VCS engine

**Loses:**
- Feature flags add code complexity (dead code paths, flag cleanup)
- Not all changes can be feature-flagged (large refactors, schema changes)
- Requires team discipline -- not enforceable by the tool alone
- Does not help solo developers who branch for experimentation
- Conflicts still occur on the remaining cases -- this is a reduction, not elimination

**Complexity:**
- VCS engine: None (this is a workflow, not a VCS feature)
- Platform: Low (giti could promote trunk-based workflow but cannot enforce it)
- Developer mental model: Medium (requires understanding feature flags and continuous integration)

**Prior art:**
- Google: Trunk-based development with feature flags at massive scale. Source: trunkbaseddevelopment.com, Atlassian documentation
- Meta (Sapling): Stacked diffs model is essentially trunk-based with very short-lived branches. Source: engineering.fb.com
- Atlassian: "With only one branch, merging is not required, eliminating merge conflicts." Source: atlassian.com/continuous-delivery/continuous-integration/trunk-based-development

## Trade-off Matrix

| Dimension | A: jj Conflicts-as-Data | B: Pijul Math Patches | C: AST Semantic Merge | D: Compiler-Assisted | E: Trunk-Based Prevention |
|---|---|---|---|---|---|
| Developer ergonomics | High (deferrable, undoable) | Medium (invisible math) | High (fewer false conflicts) | Very High (type-level messages) | Medium (requires discipline) |
| False conflicts eliminated | Some (deferred, not prevented) | Many (commutative patches) | Many (entity-level) | Many (entity + type level) | Most (no branches = no conflicts) |
| Semantic conflicts caught | None | None | None | Yes (type checking) | N/A (prevented, not caught) |
| VCS engine complexity | High | Very High | Low (merge driver) | Low (merge driver) | None |
| Compiler complexity | None | None | Medium (parser exposure) | High (type-diff + merge APIs) | None |
| Prior art confidence | High (jj, growing) | Medium (Pijul, stagnant) | High (Mergiraf, Weave) | None (novel) | Very High (Google, Meta) |
| Works for non-scrml files | Yes (any file) | Yes (any file) | Yes (with parser) | No (scrml only) | Yes (any file) |

**Critical observation from the matrix:** Approaches A, C, D, and E are combinable. The optimal solution is likely a layered stack, not a single choice. Only Approach B is mutually exclusive (requires its own VCS engine).

## Open Questions

1. **What is the performance cost of running the scrml compiler during merge?** Approach D requires compiling both sides and the merged result. For a repo with 500 .scrml files where 50 are modified, how long does this take? No data exists because no tool does this.

2. **How does Approach D handle incomplete programs?** During a merge, one side may have introduced a new import that doesn't exist yet. The compiler may fail to type-check the merge not because of a conflict but because of an incomplete dependency. How does the merge tool distinguish "conflict" from "not yet complete"?

3. **Can jj's conflict model (Approach A) be implemented on top of git's object model?** jj already does this (git backend). If giti uses git underneath, can it implement jj-style conflict storage? Or does giti need to use jj itself as the backend?

4. **What happens when Approach D disagrees with the developer?** If the compiler says "this merge is type-safe" but the developer knows it's semantically wrong (business logic conflict), is there a way to flag compiler-approved merges for human review?

5. **How should non-scrml files be handled?** Approach D only works for .scrml files. A giti repo may contain .json, .css, .md, images. The conflict model must have a fallback. Is Approach C (AST merge) the fallback for parseable files and text merge the fallback for everything else?

## Recommendation for Debate

**Approaches worth debating:**
- **Approach A + C + D (Layered Stack):** jj-style conflict storage (A) as the foundation, AST-aware merge (C) for parseable files, compiler-assisted merge (D) for .scrml files specifically. This combines the strengths of all three.
- **Approach A + E (jj + Trunk-Based):** jj-style conflict storage with strong tooling nudges toward trunk-based development. Simpler than the layered stack but gives up the compiler-assisted advantage.

**Approaches that can be eliminated:**
- **Approach B (Pijul math patches) as sole model:** The theory is elegant but Pijul's near-zero adoption proves this approach cannot sustain a product. The specific benefit (commutative patches eliminating false conflicts) is largely replicated by Approach C (AST merge) with vastly better ecosystem support.
- **Git-style text markers as the conflict format:** The parent deep dive's Bryan constraint #6 explicitly rules this out. Every alternative studied is strictly superior.
- **Approach E alone (trunk-based only):** A workflow recommendation is not a VCS feature. It complements but cannot replace a conflict resolution model.

**Suggested debate framing:** "Should giti implement a layered conflict resolution stack (jj storage + AST merge + compiler type-checking) or keep it simple with jj-style storage plus strong trunk-based workflow nudges -- and is the compiler-assisted layer (Approach D) worth its novel complexity and implementation risk?"
